# Two-minute demo

Adapt the timing and content to the actual event rules.

| Time | Show | Say |
| --- | --- | --- |
| 0:00–0:15 | Project and user problem | Name the event and the user you help. |
| 0:15–0:35 | A realistic sample input | Explain what the user is trying to accomplish. |
| 0:35–1:15 | The working core flow | Show the interaction and result. Keep slides secondary. |
| 1:15–1:40 | One technical detail or validation | Explain the interesting part, what you built, and a tradeoff. |
| 1:40–2:00 | Result, limitation, and next step | Tie the demo to the rubric and acknowledge what remains. |

## Before presenting

- Open the correct project, seed sample data, and check required services.
- Rehearse once on the actual presentation device with a timer.
- Close unrelated tabs and notifications.
- Check audio, readable text, and that no keys or private data appear.
- Prepare a short screen recording and screenshots as a fallback.
- Assign one speaker and one operator if that helps the team.

## If the live demo fails

Explain the issue briefly, switch to the recording, and identify it as recorded. Distinguish the working parts from mocked or planned parts. Finish with the same result and limitations.

## Be ready for questions

Who needs this? What is different? What did the team build during the event? How do you know it works? What happens when an external service fails? What would you improve next?
